# ITER-2026-11-14-5

**Статус:** completed

## Цель

A3: вставка изображения из буфера обмена (C-IMG-04 п.2 — второй из трёх
источников обёртки). До этого среза картинку можно было выбрать только из уже
лежащих в хранилище файлов.

## Сделано

**Код (`src/core/clipboard.ts`, чистая логика):**

- `clipboardImageExtension(mime)` — MIME → расширение (png, jpg, gif, webp,
  bmp, svg); `null` для не-изображений;
- `pastedImageStamp(now)` — метка локального времени `YYYYMMDDHHmmss`;
- `buildPastedImagePath(...)` — путь `папка/Pasted image <штамп>.png` с
  подбором свободного имени (` 1`, ` 2`, …), чтобы вставка не перезаписывала
  предыдущий файл, если штамп совпал;
- `resolveAttachmentFolder(configValue, activeFileFolder)` — разбор настройки
  Obsidian `attachmentFolderPath` (`''` — корень, `'./'` — папка заметки,
  иначе путь);
- `guessAttachmentFolder(imagePaths)` — запасной вариант: самая населённая
  папка с изображениями, чтобы не создавать новую папку рядом с существующей.

**UI / плагин:**

- команда **`Create image wrapper from clipboard`**;
- кнопка **«Из буфера»** в диалоге создания обёртки (C-IMG-04 требует, чтобы
  источник выбирался там же);
- `readClipboardImage()`: сначала Electron (`clipboard.readImage` → `toPNG`) —
  только он отдаёт картинку, скопированную в другой программе; если недоступен
  (мобильные), остаётся Web Clipboard API;
- `pasteImageWrapper()`: буфер → файл в папке вложений → `ensureImageWrapper`
  → открытие созданной обёртки. Каждый шаг с отказом даёт понятное уведомление
  (нет картинки в буфере / не удалось сохранить файл / не удалось создать
  обёртку), а не молчание.

**Тесты (+7, всего 132):** штамп времени, MIME → расширение, путь в папке и в
корне, занятые имена, настройка папки Obsidian (включая `./` и мусор),
`guessAttachmentFolder`.

## Найденный дефект

Собственные тесты поймали ошибку в уже существующем коде:
`normalizeAttachmentPath` не отбрасывал **конечный** слэш, поэтому склейка
«папка/файл» давала `img//Pasted image ….png` (`resolveAttachmentFolder`
возвращал `attachment/` для `/attachment/`). Исправлено в одном месте —
`normalizeAttachmentPath`, добавлен тест на правило «путь всегда указывает на
файл». Это же правило чинит разбор папки вложений.

## Решения

1. **Имя файла повторяет формат Obsidian** (`Pasted image <штамп>.png`), чтобы
   вложения из буфера не выбивались из остальных файлов хранилища.
2. **Папка вложений — из настроек Obsidian, без новой настройки плагина.**
   Контракт не меняется (settings остаются 12), и картинка попадает туда же,
   куда её кладёт сам Obsidian. Если настройку прочитать не удалось — самая
   населённая папка с изображениями.
3. **Непроверяемая часть изолирована.** Чтение буфера — единственный код,
   который нельзя покрыть тестами вне Obsidian; он собран в одном методе
   `readClipboardImage` и окружён обработкой ошибок, а всё остальное (имя,
   папка, расширение) — чистая логика с тестами.
4. **Вставка в тело заметки не переопределяется.** Obsidian сам вставляет
   картинку в редактор; срез добавляет то, чего у него нет — объект-обёртку
   `image` с обязательным `attachment` (INV-24).

## Правки после проверки пользователем

### П-1. Файл, скопированный в проводнике, «не виделся»

`clipboard.readImage()` отдаёт только **растровое** изображение (CF_BITMAP).
Когда файл копируют в проводнике Windows, в буфере лежит **список путей**
(CF_HDROP), а растровой картинки нет вообще — `readImage()` возвращает пустое
изображение, и команда сообщала «в буфере нет изображения». Копирование из
браузера работало, потому что там как раз кладётся растр.

Решение: `readClipboardSources()` перебирает случаи по приоритету:

1. растровая картинка (браузер, редактор) — как раньше;
2. файлы из проводника: `FileNameW` (UTF-16LE), `FileName`, `text/uri-list`,
   `text/plain` → пути проверяются на существование и на расширение
   изображения, затем читаются с диска (Node `fs`) и попадают в vault;
3. запасной путь — Web Clipboard API (`text/uri-list`).

Имена: файл с диска сохраняется под исходным именем (`cover.png`, при
занятости — `cover 1.png`), растровая вставка — `Pasted image <штамп>.png`.
Несколько скопированных файлов создают несколько обёрток за один вызов.

Разбор форматов вынесен в core: `parseFileNameW`, `parseUriList`,
`parsePathList`, `pickImageFilePaths`, `buildImportedImagePath` — покрыты
тестами, включая кириллицу в пути (UTF-16LE) и отбрасывание UNC-путей.

### П-2. Пустая галерея вела в тупик

Если свободных изображений не осталось, команда показывала уведомление и
ничего не делала. Теперь она сначала пробует буфер обмена: если там есть
картинка — создаётся обёртка; уведомление появляется только когда в буфере
тоже пусто, и объясняет оба варианта.

### П-3. «Create object» → тип `image` создавал объект без `attachment`

`CORE_TYPES` содержит все 29 типов ядра, включая `image`, поэтому диалог
создания объекта предлагал и его. В результате появлялся объект `image` без
`attachment` — прямое нарушение INV-24 и обход правила «один файл — одна
обёртка» (C-IMG-05).

Решение: `image` убран из списка типов в диалоге, а в `createObject` осталась
защита: при вызове в обход списка показывается подсказка и открывается обычный
поток создания обёртки, а не создаётся неполный объект.

## Найденный дефект (2)

Тест на разбор `text/uri-list` поймал ошибку в `uriToPath`: UNC-путь
(`file://server/share/…`) не отбрасывался, потому что после `file://` идёт имя
хоста без ведущего слэша. Исправлено: путь без ведущего слэша считается
сетевым и не импортируется.

Процесс: литеральная замена большого блока с табами оказалась ненадёжной, и
метод `pasteImageWrapper` был заменён сплайсом по номерам строк с проверкой
границ (сигнатура, маркер конца, закрывающая скобка) — временный скрипт удалён
после применения.
