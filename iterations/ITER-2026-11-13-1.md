## Дефект, найденный при приёмке (14.11.2026)

**Симптом.** При включении плагина Obsidian сообщал:

```
Plugin failure: meta-kb TypeError: Class extends value undefined is not a constructor or null
    at anonymous (plugin:meta-kb:800:19)
```

**Причина.** Циклический импорт. `ui/modals/FieldModal.ts` импортировал всех
наследников (нужны фабрике `openFieldModal`), а каждый наследник импортировал
`FieldModal` (нужен для `extends`). esbuild разворачивает наследников раньше
базы, поэтому в бандле `StringModal` объявлялся до `FieldModal` — класс
наследовал ещё не инициализированное значение.

**Масштаб.** Дефект существовал с ITER-2026-11-06-0: сборка
`sandbox/plugin/main.js` от 06.11 имеет тот же порядок (`StringModal` — 617,
`FieldModal` — 1015). То есть плагин не загружался ни разу.

**Почему не поймали.** `tsc` и esbuild проверяют типы и синтаксис, но не
порядок инициализации модулей. Приёмка предыдущего среза была отчётом агента
(«✅ 6/6 требований»), а не фактической загрузкой бандла. Это ровно тот
анти-паттерн, против которого вводился принцип «отчёт — вывод команд».

**Исправление.** Базовый класс вынесен в `ui/modals/BaseFieldModal.ts`, у
которого нет обратных зависимостей. Наследники импортируют базу, а
`FieldModal.ts` остался фабрикой и реэкспортирует `FieldModal` /
`FieldModalParams` для существующих потребителей. Цикл разорван: база — лист
графа зависимостей.

**Новые ворота G3c — `npm run check:bundle`.**
`tools/check-bundle.mjs` загружает собранный `main.js` в Node с заглушкой
модуля `obsidian` и проверяет, что экспортируется класс плагина с `onload()`.
Falsification (проверено): против старой сборки ворота падают с тем же
сообщением — `Class extends value undefined ... sandbox/plugin/main.js:617:19`;
против исправленной — `check:bundle OK`.

**Побочно исправлено.** `tools/install-vault.mjs` ставил сборку в папку
`manifest.id` (`meta-kb`), тогда как в vault плагин лежал в `meta_kb`. Теперь
папка определяется по уже установленному плагину с тем же `manifest.id`.
