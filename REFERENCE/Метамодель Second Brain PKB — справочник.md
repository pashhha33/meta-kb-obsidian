# Метамодель Second Brain PKB — справочник

Справочник по метамодели из репозитория pashhha33/Second-Brain-PKB\_v2 для будущей разработки плагина. Состояние репозитория: конец iter-015 (2026-10-29). Схемы JSON и код опущены: оставлены типы, свойства, типы значений, правила и поведение плагина.

## 0. Как читать

- **Источники:** нормативные документы `docs/metamodel/00–10`, правила `docs/validation/00–03`, ограничения из `schema/` (только как источник норм), `plugin/README.md`. ADR, журнал решений и отчёты итераций вычитаны выборочно — через ссылки в нормативных текстах.
- **Обозначения:** INV-NN — инвариант, DL-NNN — запись журнала решений, ADR-NNN — архитектурное решение, Q-NNN — открытый вопрос.
- **Языки:** ключи и идентификаторы — английский ASCII; `title` определений (ядро и пользовательские) — русский; `title` десяти встроенных метатипов — английский, русское имя в `aliases[1]`.
- **Нормативность:** формулировки инвариантов (INV) главнее схем и правил; при расхождении побеждает документ инвариантов.

## 1. Суть и принципы

Метамодель — **самоопределяющаяся объектная модель**: тип, свойство, отношение, домен, категория, фасет, правило валидации, правило развёртывания полей и автоматизация сами являются объектами с `id` и `type`. Каждая заметка Obsidian (`.md`) — один объект, данные лежат в YAML frontmatter. Метамодель не перечисляет предметные типы (Person, Book…), а задаёт правила, по которым их можно добавлять без изменения кода плагина.

Четыре принципа:

1. **Самоопределение** — всё имеет `id` и `type`.
2. **Расширяемость без правки плагина** — новый тип, свойство, отношение, правило = новая заметка.
3. **Явная семантика** — у каждого объекта есть слой, статус и владелец.
4. **Проверяемость** — правила валидации тоже объекты; их можно добавлять и отключать.

Ограничения реализации: плагин на TypeScript и Obsidian API, офлайн, без рантайм-зависимостей без ADR; документация по-русски, код и схемы по-английски.

**Размер модели:**

## 2. Три слоя

| Признак | `system` | `classification` | `content` |
| --- | --- | --- | --- |
| Назначение | описать, как устроена модель | описать, как объекты группируются | хранить знания |
| Состав | метатипы, определения типов, свойств, отношений, правила валидации, автоматизации, правила развёртывания | домены, узлы иерархических категорий, фасеты, значения фасетов | экземпляры типов (ядро из 29 типов и пользовательские) |
| `type` | `type`, `property`, `relation`, `automation`, `validation-rule`, `field-expansion` | `domain`, `hierarchical-category`, `facet`, `facet-value` | любые остальные |
| Кто создаёт | автор модели или bootstrap | автор модели | пользователь |
| Влияние правки | на все объекты типа | на группировку и навигацию | на один объект |

**Правило согласования (INV-09):** `layer` — явное свойство, не выводится из имени файла или пути. Расхождение `layer` и `type` — ошибка данных. Примечание: в тексте INV-09 `field-expansion` не упомянут, но схема относит его к `system` (расхождение зафиксировано в ADR-009).

**Самоописание:** `defined_by` замыкается на метатипе `type`, у которого `defined_by` равен собственному `id` — единственная допустимая самоотсылка. Внешний реестр «типов типов» не нужен.

**Слой классификации — три независимых механизма:**

- **Domain** — крупная предметная область верхнего уровня, не иерархичен, не пересекается по смыслу.
- **Hierarchical category** — узел дерева внутри домена. Иерархия через отношение `parent`, домен через `category-domain` (1..1). Устаревший термин `taxonomy` не рекомендуется.
- **Facet** — независимое измерение (Формат, Год, Статус проработки); не дерево, значения равноправны. Значения — отдельные объекты `facet-value` с обязательным ключом `facet` (ссылка на фасет, 1..1). Отдельные объекты вместо строкового перечисления нужны, чтобы значение можно было переименовать, перевести в `deprecated` и увидеть в графе.

Привязка знания к классификации: отношения `object-category` и `object-facet-value`. Домен объекта вычисляется из домена его категорий и отдельно не хранится.

## 3. Идентичность объекта и обязательные свойства

Восемь обязательных свойств есть у любого объекта на любом слое:

| Ключ | Тип значения | Правило |
| --- | --- | --- |
| `id` | `uuid` | UUIDv7 (RFC 9562), строчная каноническая форма, 36 символов; уникален во всём vault, включая системный слой; неизменяем навсегда (INV-01…03) |
| `type` | `string` | ASCII kebab-case `[a-z0-9]+(-[a-z0-9]+)*`; множество значений открыто; после `accepted` менять не рекомендуется (INV-04) |
| `defined_by` | `uuid` (сырая строка, не ссылка) | `id` определения типа в системном слое (`type: type`, `layer: system`), чей `type_value` равен `type` объекта; указывает на прямое определение, а не на предка по `extends` (INV-12) |
| `title` | `string`, непустой | читаемое имя; изменяем; не уникален (INV-07) |
| `aliases` | `list<string>`, не меньше одного | `aliases[0]` всегда равен `title` (INV-08) |
| `layer` | `enum` | `system` / `classification` / `content`, согласован с `type` (INV-09) |
| `status` | `enum` | `draft` / `accepted` / `deprecated` (INV-10) |
| `owner` | `string`, непустой | ответственный; по умолчанию `human`; не ссылка (INV-11) |

**`type_prefix`** — производный префикс имени файла, независимо не задаётся. Алгоритм (DL-009): привести к нижнему регистру; последовательности разделителей (пробел, `_`, `.`, `/`) заменить одним дефисом; удалить всё кроме `[a-z0-9-]`; убрать дефисы по краям; если длиннее 16 символов — обрезать до 16 и убрать конечный дефис; пустой результат — объект невалиден. Единственная обрезка в реестре: `hierarchical-category` → `hierarchical-cat`. Коллизия префиксов у двух типов решается переименованием одного из них до `accepted`; ручных переопределений нет.

**Имя файла (INV-06):** `{type_prefix}_{id}.md`. `id` и префикс в имени должны совпадать со свойствами. Путь (папка) частью идентичности не является. Переименование файла нужно только при смене `type`.

**Каноническая ссылка (INV-15):** `[[{type_prefix}_{id}|{title}]]` — имя файла цели без пути и расширения, затем alias, равный `title` цели. Ссылки без alias, ссылки по `title` и ссылки с путём не канонические; плагин нормализует их. Единственное исключение — `defined_by` (сырой UUID для машинной проверки).

**Пустое значение свойства** — отсутствие ключа в frontmatter, а не пустая строка и не `null`.

**Статусы (INV-10):**

- `draft` — свободная правка; экземпляры черновых типов не основа автоматизаций; правила в `draft` не применяются.
- `accepted` — стабильно: действуют ограничения на смену `type`, `type_value`, `property_key`, `relation_key`, `value_type`, `extends`.
- `deprecated` — выведен из эксплуатации, но сохранён: ссылки остаются действительными, новые объекты по нему не создаются, обратимо. Встроенные метатипы в `deprecated` не переводятся.

Префиксы файлов равны `type`, кроме `hierarchical-category` → `hierarchical-cat`.

**Правила реестра:** метатипы не удаляются, не переименовываются и не переводятся в `deprecated`; в наследовании не участвуют (ни родитель, ни потомок); новый метатип добавляется только через DL (так добавлены `facet-value` в iter-003 и `field-expansion` в iter-006); пользовательские типы и типы ядра в этот реестр не входят; при инициализации хранилища (bootstrap) создаются десять заметок метатипов.

**Пробел:** для `automation` ни служебные ключи, ни схема, ни правила не описаны — метатип зарезервирован (назначение: триггер → действие, например синхронизация `aliases[0]` с `title`, простановка `status`).

У остальных реестров (свойства, отношения классификации и ядра) `id` определений тоже фиксированы и выданы один раз по детерминированному правилу (UUIDv7: метка времени от 2026-10-27 12:00 UTC плюс смещение, случайные части — из SHA-256 от строки вида `SecondBrainPKB/<итерация>/<имя>`). Полные значения — в `docs/metamodel/03-builtin-types.md`, `04-properties.md`, `06-relations.md`, `07-core-properties.md`. Типы ядра и правила (развёртывания, валидации) фиксированных `id` не имеют.

## 6. Типы значений (`value_type`)

Набор закрыт: 14 значений, новое — только через DL. Неизменяем после `accepted` (INV-21). Значений `object` и `json` нет — вложенных структур в модели нет.

| `value_type` | Хранение в frontmatter | Примечание |
| --- | --- | --- |
| `string` | строка | короткое значение |
| `text` | строка или блочный скаляр | многострочный текст без разметки модели |
| `number` | число | без единиц измерения в значении |
| `boolean` | `true` / `false` |  |
| `date` | ISO 8601, без времени | `2026-10-27` |
| `datetime` | ISO 8601 с временем и смещением | в ядре не используется |
| `enum` | строка из `enum_values` | одиночный выбор |
| `list<string>` | список строк |  |
| `list<enum>` | список строк из `enum_values` | мультивыбор |
| `link` | каноническая ссылка (INV-15) | значение отношения кратности 0..1 / 1..1 |
| `list<link>` | список канонических ссылок | кратность 0..\* / 1..\* |
| `uuid` | сырая строка UUIDv7 | только там, где ссылка нужна машине (`defined_by`) |
| `media` | каноническая ссылка на объект `image` | не путь к файлу (INV-23) |
| `list<media>` | список ссылок на объекты `image` | галерея миниатюр |

**Правила:**

1. `enum` и `list<enum>` требуют непустой `enum_values` в определении.
2. Открытые наборы (формат, год, статус проработки) моделируются фасетом и его значениями, а не `enum`.
3. `enum_values` можно расширять, но не сужать. Удаление значения — только с проверкой данных: значения вне набора помечаются правилом, но не удаляются.
4. Пустое значение — отсутствие ключа.
5. Смена `value_type` у принятого определения — новое определение и `deprecated` старого.

## 7. Свойства

Свойство — объект `type: property` в системном слое. Значение хранится в frontmatter под ключом `property_key`.

**Пара key / label (INV-16, INV-22).** `key` — машинный идентификатор (`property_key`, `relation_key`, `type_value`); `label` — человекочитаемое имя и равно `title` определения (отдельного поля `label` нет). В интерфейсе основное имя — `label`, `key` показывается как индикатор (вторая строка, бейдж, подсказка). `aliases[1]` определения хранит `key`, поэтому поиск работает и по русскому имени, и по ключу.

**Ключи определения свойства:**

| Ключ | Тип | Обязательность | Смысл |
| --- | --- | --- | --- |
| `property_key` | `string`, ASCII, допускает `_` и `-` | always | уникален в vault, неизменяем после `accepted` |
| `value_type` | `enum` | always | один из 14 типов значений |
| `required` | `enum` | always | `always` (у всех объектов области) или `conditional` |
| `applies_to` | `"*"` или список `type_value` | always | область применения; наследуется потомками типа, снимается через `excludes` |
| `enum_values` | `list<string>` | conditional | обязателен при `enum` / `list<enum>` |

Изменение `applies_to` у принятого определения допустимо; при сужении значения вне области остаются в данных, помечаются правилом, но не удаляются.

## 8. Отношения

Отношение — объект `type: relation`. Значение хранится **в объекте-источнике**, в frontmatter под ключом `relation_key`, в канонической ссылке (одиночной или списком). Обратные направления не хранятся: плагин вычисляет их и показывает как входящие связи.

**Ключи определения:** `relation_key` (уникален, неизменяем); `source_type` и `target_type` — списки `type_value`, значение `*` означает «любой тип слоя `content`»; область наследуется по `extends`; `cardinality` — `0..1`, `1..1`, `0..*`, `1..*`; `inverse_key` — только если обратная связь хранится явно (в реестре не используется).

**Форма значения по кратности:** при `0..1` и `1..1` — одиночная ссылка, не список; при `0..*` и `1..*` — ссылка или список; при `1..1` и `1..*` значение обязательно. Форма значения выводится из кратности (отдельный `value_type` в примерах определений не задан, см. раздел 16).

### 8.1 Отношения классификации (4)

| Ключ | Label | Источник | Цель | Кратность |
| --- | --- | --- | --- | --- |
| `parent` | Родительская категория | `hierarchical-category` | `hierarchical-category` | 0..1 |
| `category-domain` | Домен категории | `hierarchical-category` | `domain` | 1..1 |
| `object-category` | Категория объекта | любой тип слоя `content` | `hierarchical-category` | 0..\* |
| `object-facet-value` | Значение фасета | любой тип слоя `content` | `facet-value` | 0..\* |

У корня дерева категорий `parent` отсутствует; циклы запрещены; все узлы ветки принадлежат одному домену. Отношения «объект → домен» нет: домен выводится через категории.

### 8.2 Отношения ядра (14)

| Ключ | Label | Источник | Цель | Кратность | Обратная подпись |
| --- | --- | --- | --- | --- | --- |
| `author` | Автор | `source`, `quote` | `person`, `organization` | 0..\* | Работы автора |
| `about` | О чём | `*` | `*` | 0..\* | Упоминается в |
| `part-of` | Часть целого | `*` | `*` | 0..\* | Составляющие |
| `participant` | Участник | `event`, `task`, `project` | `person`, `organization` | 0..\* | Участвует в |
| `derived-from` | Произведено из | `note`, `image`, `decision` | `source`, `file`, `note` | 0..\* | Послужило основой для |
| `supports` | Поддерживает | `note`, `decision`, `source` | `claim`, `question`, `decision`, `goal` | 0..\* | Подтверждается |
| `blocks` | Блокирует | `task`, `goal`, `decision`, `project` | `task`, `goal`, `decision`, `project` | 0..\* | Заблокировано |
| `located-in` | Находится в | `event`, `place`, `person`, `organization` | `place` | 0..\* | Расположены здесь |
| `member-of` | Состоит в | `person`, `organization` | `organization` | 0..\* | Участники |
| `references` | Ссылается на | `note`, `source`, `file`, `organization` | `*` | 0..\* | Упомянуто в |

| `part-of-collection` | Элемент коллекции | `film`, `track`, `image` | `film-series`, `album`, `gallery` | 0..\* | Элементы коллекции |
| `narrator` | Чтец | `source` | `person` | 0..\* | Озвученные работы |

**Правила:**

1. `part-of` и `blocks` ацикличны; `contradicts` симметрично (хранится только в источнике, показывается в обе стороны).
2. `derived-from` отличается от `references` производностью: знание получено из цели (цитата из книги), а не просто упоминает её.
3. Принадлежность коллекции и главе хранится со стороны элемента (`part-of-collection`, `chapter-of`); коллекция и книга списка элементов не хранят. Порядок — свойством `position` элемента.
4. Приоритет частных отношений: если для пары типов есть `chapter-of` или `part-of-collection`, общий `part-of` для неё не используется.
5. Связи с персонами выражаются отношениями, а не свойствами (поэтому `narrator`, а не поле).
6. Отношения вне реестра (`answers`, `owns`, `precedes`) пользователь создаёт как объекты `type: relation`.
7. Отношение ядра можно перевести в `deprecated`: значения в заметках остаются, новые связи плагин не предлагает.

## 9. Наследование типов

Тип — объект `type: type` (системный слой), экземпляры — слой `content`.

- `extends` — ссылка на другой тип, 0..1. Родитель не может быть метатипом. Цепочка линейна и ациклична; глубина до 5 рекомендуется, больше — предупреждение. После `accepted` не меняется.
- `type_value` **не наследуется**: у потомка собственное уникальное значение; `defined_by` экземпляра указывает на прямое определение потомка, принадлежность предку (`is_a`) вычисляется по цепочке.
- `excludes` — список ключей свойств и отношений, исключённых у типа и его потомков. Каждый ключ должен существовать и реально входить в набор цепочки. Универсальные обязательные свойства и `type_value` исключать нельзя. Потомок снимает исключение, перечислив ключ в своём `field_order`.
- `field_order` — порядок собственных полей типа; допускаются только ключи из набора цепочки.
- **Эффективный набор полей типа:** ключ входит, если `applies_to` определения равен `*` либо содержит тип или любого его предка, и ключ не исключён. **Nearest wins:** ключ, объявленный на нескольких уровнях, входит один раз и принадлежит ближайшему к листу уровню.
- **Порядок представления** (одинаков для форм плагина и валидации): универсальные обязательные свойства → унаследованные поля от корня к листу (внутри уровня по возрастанию `id` определения) → собственные поля по `field_order`, остальные — по возрастанию `id`.
- Параметры поля (`value_type`, `required`, `cardinality`, `enum_values`, `label`) на уровне типа не переопределяются (открыт Q-003).
- Абстрактных типов нет: экземпляры бывают и у корней цепочек.

## 10. Жизненный цикл определений и `deprecated`

Общие правила: `deprecated` — не удаление; `id` не меняется; ссылки действительны; перевод обратим; новые объекты по устаревшему определению не создаются.

| Что в `deprecated` | Последствия |
| --- | --- |
| Тип | экземпляры остаются валидными, новые не создаются, `type_value` не переиспользуется; миграция только созданием новых объектов с новым `id` и пометкой старого; автоправка `type` и `defined_by` запрещена; перед переводом — зафиксировать причину и план в теле заметки |
| Предок в цепочке | потомки и их экземпляры остаются валидными, в `deprecated` автоматически не переходят; плагин помечает цепочку и предупреждает при создании экземпляров потомка |
| Объект классификации | виден с пометкой; новые привязки не предлагаются; существующие сохраняются; потомки категории не переводятся автоматически, ветка помечается целиком |
| Свойство или отношение | значения в заметках сохраняются; плагин не предлагает его в формах и не создаёт связи; перенос значений — только явной автоматизацией или вручную |
| Правило развёртывания или валидации | не применяется; данные объектов не меняются |
| Метатип | запрещено (INV-14) |

| Роль | Состав экземпляра |
| --- | --- |
| Карточка | только метаданные (`title`, `author`, `isbn`, `published`, `cover`) |

### 11.2 Обёртка `image` (INV-23, INV-24)

`image` — объект-обёртка, а не файл. `attachment` (путь к вложению Obsidian) обязателен. Сам файл — не объект модели: у него нет `id`, `type`, `layer`, он не участвует в отношениях и графе. Визуальные свойства (`cover`, `poster`, `photo`, `artwork`) ссылаются на обёртку; одна обёртка может быть значением нескольких свойств разных объектов и элементом `gallery`. Тип `file` остаётся для произвольных файлов (PDF, архив).

### 11.3 Принципы расширения

- Новый тип — новая заметка `type: type`, код не меняется.
- Форматы и варианты не становятся типами: различия в составе полей (`book` + формат, `person` + профессия, `image` + способ создания) выражаются развёртыванием полей, а не потомками `audiobook`, `ebook`, `ai-image`.
- Соответствие типа элемента и коллекции инвариантом не является: смешанная подборка требует отношения, созданного владельцем.

8. `deprecated` не освобождает ни `id`, ни `property_key`.

## 13. Развёртывание полей (field expansion)

Состав полей объекта зависит от значения свойства-триггера. Правило — отдельный объект `type: field-expansion`, а не вложенная структура в определении типа; код плагина при добавлении правила не меняется. Развёртывание **дополняет** наследование: `extends` задаёт постоянный состав полей типа, правило — состав, зависящий от данных экземпляра.

**Объект правила** (системный слой, `defined_by` = метатип 10; `id` не фиксирован):

| Ключ | Тип | Смысл |
| --- | --- | --- |
| `applies_to_type` | `list<string>`, непустой | `type_value` типов; действует и на потомков по `extends` |
| `trigger_property` | `string` | `property_key` свойства с `enum` / `list<enum>` |
| `trigger_values` | `list<string>`, непустой | подмножество `enum_values` триггера; срабатывает при совпадении любого значения |
| `adds_properties` | `list<string>` | `property_key` добавляемых свойств |
| `adds_relations` | `list<string>` | `relation_key` добавляемых отношений |
| `mode` | `enum` | в v1 единственное значение — `union` |

Хотя бы один из `adds_*` непуст; ссылки на определения — по ключам (а не по `id`); все упомянутые определения обязаны существовать; дубликатов в списках нет; правило не переопределяет `value_type`, `required`, `cardinality`, `applies_to`; в `draft` и `deprecated` не применяется. Одно свойство может быть триггером нескольких правил, одно поле — добавляться несколькими.

**Когда правило активно для объекта:** `status: accepted` **и** тип объекта или его предок входит в `applies_to_type` **и** значение триггера пересекается с `trigger_values` (для `enum` — вхождение, для `list<enum>` — непустое пересечение; точное совпадение строки, регистр и пробелы значимы). Нет значения триггера — правило неактивно.

**Вычисление эффективного набора полей экземпляра (INV-26):**

1. Взять эффективный набор типа по цепочке `extends` с учётом `excludes` и nearest wins.
2. Отобрать правила `type: field-expansion`, `status: accepted`.
3. Отфильтровать по типу и по значению триггера.
4. Объединить `adds_properties` и `adds_relations` активных правил с набором типа как множества (дубликаты схлопываются).
5. Порядок: поля типа, затем добавленные — по возрастанию `id` правил, внутри правила сначала свойства, затем отношения; `field_order` типа переопределяет порядок.

Если добавленное правилом поле исключено у типа через `excludes`, исключение приоритетнее. Объединение идемпотентно и коммутативно. Режимы `first-match` и `override` отклонены.

**Канонические примеры** (необязательны, создаются владельцем):

| Тип + триггер | Значение триггера | Добавляется |
| --- | --- | --- |
| `person` + `occupation` (правило 1) | `developer`, `designer`, `researcher`, `teacher`, `writer` | свойство `specialization` |
| `person` + `occupation` (правило 2) | `developer`, `researcher`, `teacher`, `manager` | отношение `member-of` |
| `book` + `format` | `paper` | `page-count` |
| `book` + `format` | `ebook` | `attachment`, `url` |
| `book` + `format` | `audiobook` | `duration`, отношение `narrator` |
| `image` + `creation-method` | `ai-generated` | `model`, `prompt`, `seed` |

Персона с `occupation: [developer, teacher]` активирует оба правила и получает и `specialization`, и `member-of`.

**Смена или удаление значения триггера (INV-27): данные не удаляются.**

| Сценарий | Поля | Значения в frontmatter | Интерфейс |
| --- | --- | --- | --- |
| значение добавлено | развёрнуты | вводит владелец | поле в форме |
| заменено на другое из набора того же правила | без изменений | сохраняются | без изменений |
| заменено так, что правило неактивно / значение удалено | неактивны | сохраняются | скрыты, предупреждение |
| правило переведено в `deprecated` | неактивны у всех объектов | сохраняются | скрыты, предупреждение |
| значение возвращено | снова активны | прежние значения видны | поле в форме |

Очистка неактивных полей — только явная команда владельца с подтверждением. Обязательность значения в развёрнутом поле не выражается (ключ `requires_properties` не принят, Q-003).

## 14. Правила валидации

Правило — объект `type: validation-rule` (системный слой, `defined_by` = метатип 5, `id` не фиксирован). Правило можно добавить, отключить (перевод в `deprecated`) и перевести в `draft` без правки кода плагина; в `draft` и `deprecated` оно не применяется. Ключи: `rule_key` (kebab-case, уникален), `checks` (ссылки на нормы: `INV-NN`, `DL-NNN` или `файл.md#раздел.пункт`), `severity`, `applies_to` (`*` или список типов), `condition` (текст условия), `message`.

**Две степени тяжести, третьей нет:** `error` — объект невалиден, не принимается как источник определений и не служит основой автоматизаций, но данные не удаляются; `warning` — данные допустимы, владелец уведомляется, сохранение не блокируется. Смена `severity` существующего правила — через DL.

**Граница «схема — правило».** Схема проверяет форму одного объекта: наличие и форма ключей, `enum` / `const` / шаблоны, условные зависимости внутри объекта. Правило проверяет всё, что требует имени файла, другого объекта, множества объектов или вычисления. Эффективный набор полей и порядок представления (INV-20, INV-26) не проверяются ни тем, ни другим — это алгоритм плагина.

| № | `rule_key` | Что проверяет | Норма | Область | Тяжесть |
| --- | --- | --- | --- | --- | --- |
| 1 | `unique-id` | `id` встречается в vault один раз | INV-02 | `*` | error |
| 2 | `filename-matches-object` | имя файла = `{type_prefix}_{id}.md` | INV-05, 06 | `*` | error |
| 3 | `aliases-first-equals-title` | `aliases[0]` = `title` | INV-08 | `*` | error |
| 4 | `media-target-is-image` | цель `media` — объект `image` | INV-23 | `*` | error |
| 5 | `image-has-attachment` | у `image` есть `attachment` | INV-24 | `image` | error |
| 6 | `extends-acyclic` | цепочка `extends` без циклов | INV-18 | `type` | error |
| 7 | `defined-by-consistent` | `defined_by` ведёт на определение с тем же `type_value`, в системном слое | INV-12, 13 | `*` | error |
| 8 | `trigger-values-subset` | `trigger_values` ⊆ `enum_values` триггера | INV-25 | `field-expansion` | error |
| 9 | `link-target-exists` | цель канонической ссылки существует и имя файла цели верно | INV-15, 23 | `*` | error |
| 10 | `unique-machine-keys` | уникальны `type_value`, `property_key`, `relation_key`, `rule_key` | INV-13, 16, 17 | определения | error |
| 11 | `relation-acyclic` | нет циклов в `parent`, `part-of`, `blocks` (графы ключей не смешиваются) | реестр отношений | `*` | error |
| 12 | `inactive-field-value` | осиротевшее значение развёрнутого поля | INV-27 | `*` | warning |
| 13 | `extends-depth` | цепочка `extends` глубже 5 | INV-18 | `type` | warning |
| 14 | `deprecated-link-target` | ссылка на объект в `deprecated` | INV-10 | `*` | warning |
| 15 | `facet-target-is-facet` | ключ `facet` указывает на `type: facet` | INV-15 | `facet-value` | error |
| 16 | `collection-element-consistent` | фильм — в серию, трек — в альбом, изображение — в галерею | DL-025 | `film`, `track`, `image` | warning |
| 17 | `relation-endpoints-match` | тип источника и каждой цели входит в область отношения (с наследованием, `*` = любой `content`) | INV-17 | `*` | error |
| 18 | `relation-cardinality-form` | форма и наличие значения соответствуют кратности (список при 0..1 / 1..1 запрещён; при 1..1 / 1..\* значение обязательно) | INV-17 | `*` | error |
| 19 | `expansion-keys-exist` | определения из `trigger_property`, `adds_*`, `applies_to_type` существуют; триггер — `enum` / `list<enum>` | INV-25 | `field-expansion` | error |

Правило 5 дублирует схему: требование `attachment` выражено и в схеме, но правило нужно для объектов, которые схемой не проверялись (импорт, ручная правка).

**Кандидаты следующих волн (14, не реализованы):** файл по пути `attachment` существует; alias ссылки равен `title` цели; `aliases[1]` определения равен ключу; родитель `extends` не метатип; `excludes` и `field_order` содержат только ключи цепочки; значение свойства соответствует `applies_to` определения; значение `enum` принадлежит `enum_values`; форма значений по `value_type` для одиннадцати ключей ядра и значений отношений; согласованность `category-domain` в ветке; дубли ключей во frontmatter; коллизия `type_prefix`; `format: audiobook` без `attachment` и `duration`; `requires_properties` (механизм не принят); матрица «тип элемента → тип коллекции» (не введена). Два отложены сознательно: они требуют полного реестра определений и делаются вместе с bootstrap.

## 15. Поведение будущего плагина

### 15.1 Общий контракт создания и хранения

1. **Создание объекта:** сгенерировать UUIDv7, вычислить `type_prefix`, сформировать имя файла, записать восемь обязательных свойств, `aliases[0] = title`; `layer` по соответствию с `type`; `status` по ситуации (из пустой ссылки — `draft`); `owner` — владелец хранилища.
2. **Нормализация ссылок** к канонической форме `[[{type_prefix}_{id}|{title}]]` при сохранении и по явной команде; при изменении `title` цели обновлять alias во всех ссылках (цель не меняется).
3. **Объект с нарушением** инвариантов не считается принятым и не используется как источник определений.
4. **Редактирование по ключам, отображение по label:** формы показывают `label` определения (с индикатором `key`), а пишут в frontmatter под `property_key` / `relation_key`. Если штатный виджет свойств Obsidian не может показать `label` и канонические ссылки, плагин даёт собственный UI.
5. **Контроль области и кратности:** `applies_to` свойств, `cardinality` отношений; сообщения — по правилам валидации.
6. **Наследование:** вычислять эффективный набор и порядок полей по цепочке (один порядок для форм и валидации); cycle-guard при сохранении `extends`; предупреждения при глубине больше 5 и при предке в `deprecated`.
7. **Визуальные свойства** (`media`, `list<media>`): показывать превью обёртки `image`, а не текст ссылки; редактирование — выбор файла, после чего плагин создаёт или переиспользует обёртку `image` с обязательным `attachment` и пишет каноническую ссылку; галерея миниатюр для `list<media>`. Объект `image` без `attachment` сохранить нельзя; файл-вложение объектом не становится.
8. **Bootstrap:** при инициализации хранилища создать десять метатипов (по фиксированным `id`), определения встроенных свойств и четырёх отношений классификации; опционально — ядро (29 типов, 14 отношений, 23 свойства) и канонические правила развёртывания; правила валидации тоже появляются при bootstrap или создаются владельцем. Определения системного слоя создаются bootstrap или явной командой, но не из пустых ссылок.
9. **`deprecated`:** помечать в интерфейсе, не предлагать в списках выбора и формах, не создавать новые связи; ссылки сохранять; перевод статуса — только явное действие владельца.

### 15.2 Развёртывание полей

Пересчитывать эффективный набор полей объекта при открытии формы, при сохранении и по явной команде. Развёрнутые поля показывать после полей типа. Неактивные поля с непустыми значениями — в отдельной группе «Не используется» с предупреждением; очистка — явная команда с подтверждением, автоматически не удалять. При сохранении правила проверять состав (существование определений, `trigger_values` ⊆ `enum_values`, непустота `adds_*`, `mode: union`). При заполнении триггера в созданном объекте набор полей пересчитывается.

### 15.3 Видимость слоёв

- **Три тумблера** по `layer`: `system`, `classification`, `content`; глобальные для хранилища, хранятся в настройках плагина, в данные не пишутся.
- **Пресеты:** «Только знания» (виден `content`), «Модель» (видны `system` и `classification`), «Всё». Канонические пресеты доступны всегда; пользовательские добавляются в настройках, объектами модели не являются.
- **По умолчанию:** `content` и `classification` видны, `system` скрыт; есть команда «восстановить видимость по умолчанию».
- **Где фильтровать:** поиск (выдача и счётчик) и граф (глобальный и локальный: узлы и инцидентные рёбра). **Где не фильтровать:** проводник, quick switcher, панели обратных и исходящих ссылок, предпросмотр — там только отображаемое имя.
- **Что не зависит от видимости:** данные, разрешение и нормализация ссылок, наследование, развёртывание, валидация. Ссылка на объект скрытого слоя остаётся рабочей. Файлы вне модели ни к какому слою не относятся и не скрываются. Скрытие не заменяет `deprecated`.

### 15.4 Отображаемое имя (display title)

- **Источник:** `title` из frontmatter. Поверхности подмены (девять): проводник, заголовок вкладки, заголовок заметки, результаты поиска, quick switcher, подписи узлов графа, панели ссылок, всплывающий предпросмотр, поле значения свойства-ссылки в форме. В тексте заметки подмена не нужна: alias канонической ссылки уже равен `title`.
- **Не меняется:** имя файла, содержимое заметок, ссылки, `defined_by`, машинные ключи.
- **Совпадение `title`** у нескольких объектов: рядом с именем показывается индикатор — label типа объекта; для определений системного слоя — `key`. Для метатипов отображается английский `title`, русское имя — подсказка.
- **Поиск и quick switcher** сопоставляют запрос с `title`, `aliases` и ключами определений: объект находится и по русскому имени, и по машинному ключу.
- **Файлы вне модели** (нет обязательных свойств) отображаются именем файла. Объект модели без `title` — нарушение INV-07: показывается имя файла и пометка об ошибке.
- **Подмена обратима**, включается настройкой (по умолчанию включена) и обновляется при изменении frontmatter, переименовании файла и изменении раскладки.

### 15.5 Создание объектов из пустых ссылок

- **Момент:** по явной команде владельца (клик по пустой ссылке, контекстное меню), никогда автоматически при сохранении. Доступно для ссылки в теле заметки и для значения свойства или отношения.
- **Выбор типа:**

| Контекст | Тип |
| --- | --- |
| тело заметки | выбор среди `type: type` со статусом `accepted`, по `label` |
| ключ с единственной допустимой целью | этот тип без вопроса (`chapter-of` → `chapter`, `narrator` → `person`) |
| ключ с несколькими допустимыми целями | выбор среди них (`part-of-collection` → серия, альбом, галерея) |
| ключ вне реестров | как в теле заметки |

- **Исключение:** для `media` и `list<media>` создание из пустой ссылки не предлагается — обёртка `image` создаётся выбором файла.
- **Состав созданного объекта:** новый `id`; `type` и имя файла; `defined_by` выбранного типа; `title` = alias ссылки или текст цели (пробелы и регистр сохраняются); `aliases[0] = title`; `layer` по типу; `status: draft`; `owner`; остальные поля по умолчанию с учётом развёртывания. Объект всегда удовлетворяет INV-01…INV-12. Объекты системного слоя так не создаются.
- **Нормализация:** ссылка в месте создания заменяется канонической; значение записывается в тело или в ключ frontmatter.
- **Дубликаты:** перед созданием искать совпадения по `title` и `aliases` (регистр и пробелы нормализуются) и предлагать связать с существующим; создание дубля — только после подтверждения.
- **Отмена** ничего не меняет; **массовое создание** — отдельная команда с тем же порядком для каждой ссылки; ссылка с пустой целью объектом не становится (запрашивается имя). Устаревшие типы в выборе не показываются.

### 15.6 Статусы в интерфейсе

`draft` — видим, с пометкой статуса; `accepted` — без пометок; `deprecated` — виден с пометкой, исключён из списков выбора. Плагин статус сам не меняет.

## 16. Открытые вопросы, расхождения и риски

**Открытые вопросы реестра:**

- **Q-003** — переопределение параметров унаследованного поля на уровне типа не введено; практически обязательные поля (`prompt`, `seed` при ИИ-генерации) не выражаются.
- **Q-007** — согласование ролей `book` (вычисляются по данным) и триггера `format`; правило «`audiobook` без `attachment` и `duration`» не принято.
- **Q-008** — триггер по значению фасета не введён; `occupation` как закрытый `enum` расходится с идеей открытого набора через фасет.
- **Q-011** — перечень девяти поверхностей подмены имени не подтверждён Оркестратором; сверка при приёмке фазы 5.
- **Q-004** — файл `08-field-expansion.md` не растёт; расширение механизма требует разбиения через ADR. **Q-009, Q-010** — технические дефекты формулировок реестра `id` и ссылок в ADR.

**Расхождения в самих документах (зафиксированы в iter-009):**

- INV-09 не упоминает `field-expansion`, схема относит его к `system`.
- Реестр объявляет `applies_to` как `list<string>`, а встроенные определения хранят скаляр `"*"`; схема принимает обе формы.
- INV-21 и реестр требуют `value_type` у отношений, а определения отношений его не содержат; форма значения выводится из кратности.
- Ключ `required` у определения свойства присутствует во всех записях, но в реестре служебных ключей не перечислен.

**Риски и замечания для проектирования плагина (мои наблюдения по прочитанному):**

- Метатип `automation` ничем не наполнен: нет ключей, схемы и правил.
- Поле `condition` правила валидации — текст. Утверждение «правило добавляется без правки кода» на практике означает, что плагину потребуются встроенные реализации по `rule_key`, а новые правила владельца либо не исполняются, либо нужен формальный язык условий; в документах этот вопрос не решён.
- Схемы покрывают формы значений лишь 12 из 23 ключей свойств ядра; принадлежность значения `enum_values` и соответствие области `applies_to` не проверяются.
- Эффективный набор полей и порядок вычисляются только плагином — расхождения с будущим валидатором нужно предотвращать единой реализацией.
- Нумерация инвариантов стабильна: правила и документация обязаны ссылаться на текущие номера.

## 17. Чеклисты

**Новый тип.** Создать объект `type: type` (`layer: system`, `defined_by` = метатип 1): уникальный `type_value` kebab-case, `title` по-русски, `aliases = [title, type_value]`; при необходимости `extends` (не метатип, без циклов), `excludes`, `field_order`. Затем описать его свойства и отношения определениями с `applies_to` / `source_type` на этот тип.

**Новое свойство.** Объект `type: property` (`defined_by` = метатип 2): `property_key`, `value_type` из 14, `required`, `applies_to`; для `enum` / `list<enum>` — непустой `enum_values`; `aliases = [title, property_key]`.

**Новое отношение.** Объект `type: relation` (`defined_by` = метатип 3): `relation_key`, `source_type`, `target_type`, `cardinality`; значение хранится у источника канонической ссылкой.

**Новое правило развёртывания.** Объект `type: field-expansion` (`defined_by` = метатип 10): триггер `enum` / `list<enum>`, непустые `applies_to_type`, `trigger_values`, хотя бы одно из `adds_*`, `mode: union`; все ключи уже существуют.

**Новое значение классификации.** Фасет — `type: facet`; его значения — отдельные `type: facet-value` с ключом `facet`; привязка знания — `object-facet-value` (0..\*); категории — `hierarchical-category` с `parent` (0..1) и `category-domain` (1..1).

**Вывод из эксплуатации.** `status: deprecated`, а не удаление; для типа — зафиксировать причину и план по экземплярам; ссылки остаются; `type_value`, `property_key` и `id` не переиспользуются.
