# ADR-007: Переопределение обязательности свойства по типу

**Статус:** accepted
**Дата:** 2026-11-14
**Итерация:** ITER-2026-11-14-2
**Контекст:** `metamodel/properties.md` §1, §3.1; INV-24; C-IMG-05

## Контекст

`properties.md` §1 задаёт `required` как одно из `always | conditional | never`
**на свойство**. Этого достаточно для большинства свойств, но не для
`attachment`:

- `properties.md` §3.1: «`attachment` … **always** для `image` (INV-24)»;
- при этом у `file`, `source`, `note` то же свойство условно.

Одно значение `required` не может выразить правило «обязательно именно у
`image`». В контракте стояло `required: "conditional"` с пометкой в тексте
(`note`), то есть требование INV-24 существовало **только в прозе** и не было
доступно коду: валидация не смогла бы его применить, а G2 не мог проверить.

## Решение

Добавить в определение свойства необязательное поле:

```json
"required_by_type": { "image": "always" }
```

Значения — тот же enum `always | conditional | never`, ключи — `type_value`
(или `*`). Поиск при проверке идёт по цепочке `extends`, ближайший предок
побеждает; если переопределения нет — берётся `required` свойства.

Реализация: `requiredFor(propertyKey, typeValue)` в
`plugin/src/core/metamodel.ts`. Версия контракта поднята `1.1.0 → 1.2.0`.

## Альтернативы

| Вариант | Почему отклонён |
|---|---|
| Отдельное определение свойства для каждого типа (`attachment-for-image`) | размножает объекты `property`, нарушает уникальность `property_key` (INV-16) |
| Отдельный объект `property-requirement` | тяжелее: новый метатип, реестр, bootstrap; для v1 достаточно поля |
| Оставить правило только в прозе | INV-24 остаётся непроверяемым — ровно та проблема, из-за которой правило и появилось |

## Последствия

**Плюсы**

- INV-24 выражен машиночитаемо: валидация получит правило из контракта, а не из
  комментария.
- Общее поле `required` остаётся значением по умолчанию — существующие свойства
  не меняются.
- G2 проверяет, что ключи `required_by_type` ссылаются на существующие типы, а
  значения входят в enum.

**Риски и ограничения**

- Правило живёт в контракте; проза (`properties.md` §3.1) остаётся источником
  смысла. Расхождение поймает только ручное ревью — G2 сверяет наличие ключа,
  а не фразу «always для image». При необходимости можно добавить проверку по
  тексту таблицы, как сделано для `defines_layer` в types.md §1.
- Пока не решено, как выражать зависимость обязательности от **значения**
  другого свойства (например «`duration` обязателен, если `format: audiobook`»).
  Это уже не «по типу», а условное требование; отложено (см. Q-007 в `gaps.md`).
